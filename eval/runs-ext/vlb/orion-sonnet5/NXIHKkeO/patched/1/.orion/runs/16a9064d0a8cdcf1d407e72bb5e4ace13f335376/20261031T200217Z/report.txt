Two independent reasons: (1) CRC validation in CPython's zipfile only compares the final running CRC32 to the recorded value AFTER a member has been fully decompressed — it never changes what bytes come out of decompression. Since RelaxedZipFile's documented purpose (module docstring, relaxed_zipfile.py:4: "removed flag/password/filename/CRC checks to align better with PyTorch's zip decoding") is to match PyTorch's own lenient C++ zip reader (which also does not enforce CRC on checkpoint entries), picklescan and torch.load would decompress the exact same bytes from the exact same compressed stream regardless of this flag — there is no scenario where disabling CRC lets an attacker smuggle content past the scanner that differs from what PyTorch will actually execute. (2) Even if CRC were left enabled and a BadZipFile were raised mid-read, picklescan's opcode scanner (_list_globals, scanner.py:272-365) processes the pickle stream incrementally via pickletools.genops and catches any exception generically at scanner.py:285, preserving every opcode already parsed in `ops`; scan_pickle_bytes (scanner.py:406-420) then explicitly re-raises any dangerous globals found before the error via GenOpsError and reports them with scan_err=True ("Found some globals before error - could be a malicious partial pickle"). So a malicious GLOBAL/REDUCE opcode occurring before any CRC-triggered truncation point would still be flagged whether or not the CRC check is disabled. The CRC override therefore only prevents picklescan from erroring out and skipping entries that PyTorch would load anyway (closing a potential scanner-evasion-via-corruption gap), rather than opening one. This is a deliberate, documented compatibility decision, not an accidental removal of a security control with demonstrated exploit impact.
