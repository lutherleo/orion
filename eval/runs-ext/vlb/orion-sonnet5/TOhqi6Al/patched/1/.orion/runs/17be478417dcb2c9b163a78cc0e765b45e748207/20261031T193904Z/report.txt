However, the flagged subpattern ([a-z0-9%-]+\.){1,} is NOT the canonical (x+)+ catastrophic-backtracking shape it superficially resembles, because each repetition of the outer group is anchored by a mandatory literal '.' that is NOT a member of the inner character class [a-z0-9%-]. This delimiter removes the combinatorial ambiguity that causes true catastrophic backtracking: since the inner class can never consume a '.', the engine's greedy inner '+' always stops at exactly the next literal dot in the string, so for any given string there is exactly ONE way to parse each repetition (not an exponential number of ways to split a run of characters, as in true (a+)+ patterns with no delimiter). I hand-traced the proposed attack string ('a.'.repeat(30000) + an invalid trailing char) through the backtracking algorithm: the only freedom the engine has on failure is choosing how many of the (at most N) actual dot positions to use as the outer loop's repetition count (N choices, tried one at a time by unwinding the last repetition), and at each unwind step, the optional trailing groups ([a-z0-9-]+?, :(\d{1,5})?, the path group) can only examine a bounded, non-overlapping slice of the string before failing -- giving O(N) total work, not O(2^N). This is the standard "delimiter-anchored repetition" idiom that is specifically NOT vulnerable to catastrophic backtracking (distinguishing it from genuinely unsafe patterns like (\w+)+ or (a|a)+ with no inter-repetition delimiter). For N=30000 this is tens of thousands of O(1) backtrack steps -- milliseconds at most, not a meaningful denial-of-service.

I could not execute JS to get an empirical timing (no code-execution tool is available in this environment), and the exploit_search catalog had no indexed entries for this library to cross-check against a known CVE.
