# Repo-level real-vulnerability benchmarks and SAST benchmarks (incl. false-alarm sets) as candidates for benchmarking Orion

Scope note: researched 2026-10-31. Orion context used for the fit ratings (from the local repo, not the web): Orion scans whole repos, emits file / line range / function / CWE findings and SARIF, writes no exploits; its study languages are JS/TS, Python and Java; headline CVEs must post-date 2026-05-31 (latest frontier cutoff, Opus 5); its matcher credits same file plus a function-name match or a line inside the patched range +/-10 — [Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md). Orion already has OWASP BenchmarkJava (pin a0f07b8) and BenchmarkPython (pin f129148) wired into `eval/owasp.py` with a 120-case sample (`eval/dataset/owasp_sample.json`), a BountyBench adapter (`eval/bountybench.py`), and NodeGoat (15 keys) / PyGoat (16 keys) dev benchmarks — [Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md); [eval/owasp.py](file:///C:/Users/h/Downloads/orion/eval/owasp.py).

Fit rating scale used below: **High** = repo-level, Orion's languages, real or realistic bugs, line/function ground truth, measurable false alarms; **Medium** = usable with adaptation or one major caveat; **Low** = wrong language/granularity/task (exploit-only, micro-programs, C-only).

## Q1. Catalog: which whole-repo / realistic-project vulnerability benchmarks and SAST suites exist, and how do they define ground truth and scoring?

### Takeaway
There are three usable families: (a) synthetic SAST scorecard suites with built-in false-alarm cases (OWASP Benchmark Java v1.2 and Python v0.1, Juliet, CASTLE); (b) real-CVE repo-level sets with fix-commit locations (CWE-Bench-Java, OpenSSF CVE Benchmark, Vul4J/VJBench, SecBench.js, the Zhou et al. 2024 repo-level sets, ReposVul, JitVul, JavaVulBench); and (c) a new 2025-2026 wave of agentic repo-level localization benchmarks (Cisco's Vulnerability Localization Benchmark, VulnGym, SastBench, DeepSource's OpenSSF-based tool benchmark). For Orion the strongest candidates are CWE-Bench-Java, the Vulnerability Localization Benchmark, OpenSSF CVE Benchmark, VulnGym and OWASP Benchmark (Java + Python); none of them is post-May-2026, so they are dev benchmarks, not contamination-free test sets.

#### A. Synthetic SAST scorecard suites (with false-alarm cases)

- **OWASP Benchmark for Java v1.2** — current latest release is v1.2; it is a runnable Java web app analyzable by SAST, DAST and IAST tools, whose vulnerabilities are meant to be actually exploitable; license GPL-2.0; expected results in `expectedresults-1.2.csv`; scoring lives in BenchmarkUtils — [BenchmarkJava](https://github.com/OWASP-Benchmark/BenchmarkJava); [OWASP Benchmark project](https://owasp.org/www-project-benchmark/).
  - v1.2 has 2,740 test cases: Command Injection (CWE-78) 251, Weak Cryptography (327) 246, Weak Hashing (328) 236, LDAP Injection (90) 59, Path Traversal (22) 268, Secure Cookie Flag (614) 67, SQL Injection (89) 504, Trust Boundary Violation (501) 126, Weak Randomness (330) 493, XPath Injection (643) 35, XSS (79) 455 — [OWASP wiki](https://wiki.owasp.org/index.php/Benchmark).
  - Scoring: TPR = TP/(TP+FN), FPR = FP/(FP+TN), score = TPR - FPR normalized to 0-100, i.e. a Youden index; 0 = random guessing, negative = FPR exceeds TPR — [OWASP wiki](https://wiki.owasp.org/index.php/Benchmark).
  - The true-vulnerable vs safe split per category is not on the project pages; it is in the expected-results CSV — [Python test-case tab](https://raw.githubusercontent.com/OWASP/www-project-benchmark/master/tab_python_test_cases.md); [OWASP wiki](https://wiki.owasp.org/index.php/Benchmark).
  - Orion-specific caveat already logged: Krish must decide on "the Java OWASP comments that hint the answer (17/30 traps)" before scored runs; Orion's `strip_answers` removes the answer CSV, per-case XML and scorecards — [Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md).
- **OWASP Benchmark for Python v0.1** — "preliminary initial release", fully runnable Python web app, `expectedresults-0.1.csv`, license GPL-3.0 on the repo — [BenchmarkPython](https://github.com/OWASP-Benchmark/BenchmarkPython). The project page said a v1.0 was planned for early 2026 — [OWASP Benchmark project (search snippet)](https://owasp.org/www-project-benchmark/).
  - 1,230 test cases: Code Injection (94) 53, Command Injection (78) 20, Deserialization (502) 54, LDAP (90) 29, Path Traversal (22) 168, Secure Cookie (614) 39, SQLi (89) 16, Trust Boundary (501) 37, Unchecked Redirects (601) 34, Weak Hashing (328) 151, Weak Randomness (330) 326, XPath (643) 186, XSS (79) 89, XXE (611) 28; Weak Crypto (327) and ReDoS (1333) under consideration; development mostly by AppSecAI — [Python test-case tab](https://raw.githubusercontent.com/OWASP/www-project-benchmark/master/tab_python_test_cases.md).
  - Frameworks are not named on the page — [Python test-case tab](https://raw.githubusercontent.com/OWASP/www-project-benchmark/master/tab_python_test_cases.md).
- **NIST Juliet 1.3** — C/C++ part has 64,099 cases — [NIST TN 1995](https://nvlpubs.nist.gov/nistpubs/TechnicalNotes/NIST.TN.1995.pdf); the SARD listing for Java 1.3 shows 28,881 — [SARD test suite 109](https://samate.nist.gov/SARD/test-suites/109?page=2866). Release-note count of fixed systematic problems differs between the NIST landing page ("about two dozen") and the PDF ("about fourteen") — [NIST TN 1995](https://nvlpubs.nist.gov/nistpubs/TechnicalNotes/NIST.TN.1995.pdf). User guides: [Juliet v1.2 Java user guide](https://samate.nist.gov/SRD/resources/Juliet_Test_Suite_v1.2_for_Java_-_User_Guide.pdf).
  - Ground-truth quality warning: NIST's SATE VI analysis "found thousands of errors in the manifest of known bugs for Juliet 1.3 C" — [SATE VI Ockham slides](https://www.nist.gov/document/sate-vi-presentation-08ockham).
- **NIST SAMATE SATE (I-VI)** — SATE VI's Ockham Sound Analysis Criteria: a tool must be claimed sound and produce findings for >= 75% of sites; one incorrect finding disqualifies; evaluated on Juliet C/C++ (19,142 buggy sites, 40 CWE groups, 46,651 warnings); Astrée and Frama-C with Eva satisfied it; report NISTIR 8304 (Black & Walia, 2020) — [NISTIR 8304](https://nvlpubs.nist.gov/nistpubs/ir/2020/NIST.IR.8304.pdf); [NIST SATE VI Ockham page](https://nist.gov/itl/ssd/software-quality-group/sate-vi-ockham-sound-analysis-criteria). No SATE after VI was found in this search (treat SATE as superseded/inactive).
- **CASTLE (2025)** — 250 compact, compilable C micro-benchmarks, one CWE each, 25 CWEs; v2 evaluates 13 static analyzers, 10 LLMs, 2 formal verifiers (v1 said 11 SAST + 11 LLMs); introduces the "CASTLE Score"; ESBMC keeps FPs low but misses non-model-checkable classes; LLMs do well on small snippets but accuracy drops and hallucinations rise as code grows; data at github.com/CASTLE-Benchmark — [CASTLE arXiv](https://arxiv.org/abs/2503.09433v2); [CASTLE v1 HTML](https://arxiv.org/html/2503.09433v1).

#### B. Real-CVE, repo-level benchmarks with fix-commit ground truth

- **CWE-Bench-Java (IRIS, ICLR 2025)** — 120 manually validated vulnerabilities, one per project, projects average ~300K LoC (max ~7M) — [IRIS ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/582d4e27fa24168f3af1f4582655034b-Abstract-Conference.html); [IRIS arXiv v2](https://arxiv.org/html/2405.17238v2).
  - 4 CWEs: CWE-22, CWE-78, CWE-79, CWE-94. `data/fix_info.csv` lists fixed methods/classes per CVE with commit, file, class, method, line ranges and signature (core methods only; tests/resources excluded); `data/project_info.csv` gives buggy and fix commit IDs; fixes as `patches/<slug>.patch`; needs Linux, JDK 7u80/8u202/17 (manual Oracle download); MIT; now "primarily hosted at the data directory of the IRIS repo"; Hugging Face copy exists — [cwe-bench-java](https://github.com/iris-sast/cwe-bench-java); [IRIS repo](https://github.com/iris-sast/iris).
  - Later papers use an expanded CWE-Bench-Java of 176 CVEs across 111 projects and 42 CWEs — [QLCoder](https://arxiv.org/html/2511.08462v2).
- **OpenSSF CVE Benchmark** — 200+ historical JS/TS CVEs; each analyzed on vulnerable AND patched codebase; credited if it alerts on the vulnerable code, an alert on the patched code is a false positive; drivers for ESLint, NodeJSScan, CodeQL; MIT; repo not archived (88 commits, open PRs) — [ossf-cve-benchmark](https://github.com/ossf-cve-benchmark/ossf-cve-benchmark). Launched at Black Hat Europe (2020) — [SecurityWeek](https://www.securityweek.com/openssf-launches-open-source-tool-evaluating-sast-products/). Main repo last updated Mar 2024; per-CVE repos Dec 2020 (search snippet) — [ossf-cve-benchmark org](https://github.com/ossf-cve-benchmark).
- **DeepSourceCorp/benchmarks (2025-2026)** — evaluates code-review and security tools on the OpenSSF CVE Benchmark: DeepSource, Claude Code, Codex, CodeRabbit, Cursor, Devin, GitLab Duo, Greptile, Semgrep; judged-results schema with TP/FP/TN/FN and a `variant` of `fixed`/`unfixed`; README "Last updated: April 12, 2026"; earlier data in `archive/sep-2025`; Apache-2.0; no numbers on the README page — [DeepSourceCorp/benchmarks](https://github.com/DeepSourceCorp/benchmarks).
- **Vul4J (MSR 2022)** — 79 reproducible vulnerabilities from 51 Java projects, 25 CWEs; built from 1,803 fix commits of 912 Project KB vulnerabilities; each with human patch and Proof-of-Vulnerability test(s); warning that several (esp. Spring) are no longer reproducible; Docker image provided — [Vul4J GitHub](https://github.com/tuhh-softsec/vul4j); [MSR 2022 entry](https://conf.researchr.org/details/msr-2022/msr-2022-data-showcase/10/Vul4J-A-Dataset-of-Reproducible-Java-Vulnerabilities-Geared-Towards-the-Study-of-Pro).
- **VJBench (ISSTA 2023, Wu et al.)** — created for APR evaluation alongside Vul4J; also VJBench-trans (transformed code); Codex fixed 10.2 (20.4%) — [arXiv 2305.18607](https://arxiv.org/abs/2305.18607v2). Size: 15 new vulns + 35 Vul4J = 50 per one benchmark page — [alphaXiv VJBench](https://alphaxiv.org/benchmarks/york-university/vjbench); LLMSecCode could reproduce 46 (15 VJBench + 31 Vul4J) — [LLMSecCode](https://arxiv.org/pdf/2408.16100). The "42" figure was not found.
- **SecBench.js (ICSE 2023)** — 600 vulnerabilities with executable exploit payload + oracle, five server-side JS classes; prototype pollution 192, ReDoS 98; found 168 mislabeled vulnerable versions in 19 packages and 20 zero-days; Node >= 16.3 — [SecBench.js GitHub](https://github.com/cristianstaicu/SecBench.js); [ICSE 2023](https://conf.researchr.org/details/icse-2023/icse-2023-technical-track/99/SecBench-js-An-Executable-Security-Benchmark-Suite-for-Server-Side-JavaScript).
- **Zhou et al. 2024, "SAST tools vs LLMs for repo-level vulnerability detection"** (arXiv 2407.16235) — claims to be first to frame repo-level detection; Java 50 projects / 87 CVEs / 3,986,848 functions (0.008% vulnerable); C 6 / 85 / 1,181,556 (0.009%); Python 78 / 98 / 312,045 (0.18%); Java and C reuse Li et al. and Lipp et al.; Python new from NVD + GitHub fix commits; labels at function level (functions modified by the fix = vulnerable); NVD data 2002-2023 — [arXiv HTML v1](https://arxiv.org/html/2407.16235v1); [abs](https://arxiv.org/abs/2407.16235).
  - Metrics: detection ratio (S1 = any vulnerable function found per CVE, S2 = all) and "marked function ratio" as FP proxy (no precision/F1) — [arXiv HTML v1](https://arxiv.org/html/2407.16235v1).
- **Li et al., ESEC/FSE 2023, "Comparison and Evaluation on SAST Tools for Java"** — 7 free/open-source tools picked from 161; synthetic + new real-world benchmark; tools detect only 12.7% of real-world vulns; even combined, 70.9% remain undetected — [FSE 2023 listing](https://2023.esec-fse.org/details/fse-2023-research-papers/21/-Remote-Comparison-and-Evaluation-on-Static-Application-Security-Testing-SAST-Tool); [SMU record](https://ink.library.smu.edu.sg/sis_research/8976).
- **Lipp, Banescu, Pretschner, ISSTA 2022** — 6 C/C++ analyzers (5 FOSS + 1 commercial), 27 projects, ~1.15 MLoC, 192 validated CVEs; tools missed 47%-80% — [TUM PDF](https://mediatum.ub.tum.de/doc/1659728/1659728.pdf); [ISSTA 2022](https://conf.researchr.org/details/issta-2022/issta-2022-technical-papers/20/An-Empirical-Study-on-the-Effectiveness-of-Static-C-C-Analyzers-for-Vulnerability-D).
- **Charoenwet et al., ISSTA 2024** — 319 real vulns, 815 vulnerability-contributing commits, 92 C/C++ projects; Cppcheck, CodeChecker, CodeQL, Flawfinder, Infer; >= 76% of warnings in vulnerable functions irrelevant; 22% of VCCs undetected; combined tools reach 78% function-level detection; CodeQL broadest coverage — [arXiv 2407.12241](https://arxiv.org/abs/2407.12241); [ISSTA 2024](https://2024.issta.org/details/issta-2024-papers/56/An-Empirical-Study-of-Static-Analysis-Tools-for-Secure-Code-Review).
- **Esposito, Falaschi, Falessi, "An Extensive Comparison of SAST Tools"** (EASE 2024) — synthetic Java codebase, ~1.5M test executions, method-level; SASTTs have high precision but low recall — [arXiv 2403.09219](https://arxiv.org/abs/2403.09219); [EASE 2024](https://conf.researchr.org/details/ease-2024/ease-2024-papers/10/An-Extensive-Comparison-of-Static-Application-Security-Testing-Tools).
- **ReposVul (ICSE 2024 Industry Challenge)** — 6,134 CVEs, 236 CWEs, 1,491 projects, four languages; LLM-based patch untangling + static analysis; inter-procedural call relations, file/function/line info — [arXiv 2401.13169](https://arxiv.org/abs/2401.13169v2); [GitHub](https://github.com/Eshe0922/ReposVul). A third party describes it as C, C++, Python and notes it depends on proxy labels and non-executable setups — [Lira et al. 2026](https://arxiv.org/pdf/2604.08417).
- **JitVul (2025)** — 879 CVEs, 91 vulnerability types; each function linked to introducing and fixing commits (vulnerable/patched pairs); interprocedural context; ReAct agents beat plain LLMs at separating vulnerable vs benign — [arXiv 2503.03586](https://arxiv.org/abs/2503.03586).
- **JavaVulBench (Jul 2026)** — ~30,600 Java methods, 1,740 CVEs, 700+ projects; method + line labels with CVE dates; random / project-disjoint / temporal / deduplicated / unseen-CWE splits; per-model pre-training contamination audit; evaluates encoders, open-weight models, GPT-4o, GPT-4.1-mini, Claude Sonnet 4; data on Zenodo — [alphaXiv 2607.02825](https://www.alphaxiv.org/abs/2607.02825).
- **Lira et al., Apr 2026** — 509 ReposVul vulnerabilities (C, C++, Python), function alone vs +callers vs +callees; Claude Haiku 4.5, GPT-4.1 Mini, GPT-5 Mini, Gemini 3 Flash; Gemini 3 Flash F1 >= 0.978 on C at ~$0.50-0.58 per configuration — [arXiv 2604.08417](https://arxiv.org/abs/2604.08417).
- **Ghera (Android)** — each benchmark = vulnerable app + malicious exploit app + secure (patched) app; 25 benchmarks originally (2017), 56 in Dec 2018, 60 in Mar 2019, 61 in 2020; BSD-3 — [Ghera paper](https://arxiv.org/pdf/1708.02380). Used to evaluate 14 free Android tools on 42 known vulns; tools were weak — [Ranganath & Mitra](https://arxiv.org/pdf/1806.09059).

#### C. 2025-2026 agentic repo-level localization / triage benchmarks

- **Vulnerability Localization Benchmark (Cisco Foundation AI, arXiv 2609.15939, 14 Sep 2026)** — 500 real vulns, 290 repos, 147 CWEs from GitHub Security Advisories with fixing commits; ecosystems Go 215 (43%), Maven 104 (21%), npm 88 (18%), pip 52 (10%), Rust 40 (8%), Composer 1; advisories 2016-2026 incl. 21 from 2026; each task pairs pre-fix and post-fix snapshots; Phase A = File F1 on vulnerable snapshot, Phase B = true-negative rate on patched snapshot; 27 LMs + 4 static tools under one agent interface; read-only terminal in Docker (no network, 15 commands, 20 turns, temp 0.3, mean of 3 runs); code + data at github.com/cisco-foundation-ai/vulnerability-localization-benchmark — [arXiv HTML](https://arxiv.org/html/2609.15939); [abs](https://arxiv.org/abs/2609.15939).
  - Strongest system 0.229 File F1; 38.4% of tasks get no correct localization from any model; only file-level metrics — [abs](https://arxiv.org/abs/2609.15939); [HTML](https://arxiv.org/html/2609.15939).
- **VulnGym (arXiv 2608.02001, 3 Aug 2026)** — 184 reviewed GitHub advisories -> 408 vulnerability entries in 23 repos, aligned to vulnerable versions; each entry has line-level entry point (EP), critical operation (CO) and trace; tasks T1 end-to-end, T2 EP identification, T3 CO localization, T4 trace construction; location match = same repo-relative path within k=5 lines; advisories published Nov 2025-Apr 2026 (pool Jan 2025-Apr 2026); scaffolds Claude Code, OpenHands, MiniSWE; no patched versions; no SAST baseline; no dataset link in the paper — [VulnGym HTML](https://arxiv.org/html/2608.02001); [abs](https://arxiv.org/abs/2608.02001v1).
- **SastBench (Rival Labs, arXiv 2601.02941, 6 Jan 2026)** — triage benchmark: 2,737 commit/CWE entries, 299 true positives (CVEs from NVD with GitHub commits, CVEFixes method) vs 2,438 approximate false positives (Semgrep free-edition findings on pre-fix repos not sharing the CVE's CWE, same-function findings removed); 38 languages, 139 CWEs; CVEs only if reported after Feb 2025; primary metric MCC; code and data said to be open-sourced but no link given — [SastBench HTML](https://arxiv.org/html/2601.02941v1).
- **"Sifting the Noise" (Xiong & Zhang, arXiv 2601.22952, Jan 2026)** — compares Aider, OpenHands, SWE-agent for SAST false-positive filtering on OWASP Benchmark and Vul4J (CodeQL alerts), Claude Sonnet 4 among backbones — [arXiv](https://arxiv.org/abs/2601.22952v1).
- **JitVul, JavaVulBench, Lira et al.** — see section B.
- **Antares (Cisco, arXiv 2608.02407)** — 350M/1B/3B localization models on Granite; "500-task evaluation sweep" (the VLB tasks); Antares-3B "approaches GPT-5.5"; < $0.002 per task — [arXiv](https://arxiv.org/abs/2608.02407).
- **"The History Is the Detector" (Wu, Eykholt, Park, Shu, Kirat, Schales, Molloy; arXiv 2609.05335, Sep 2026)** — 19,325 high-severity CVEs 2022-2026 -> 2,710 fix commits -> 1,033 detection rules in 56 CWE families (172 skills); 644 findings with runtime evidence in 14 programs; no SAST/LLM comparison in the abstract — [arXiv](https://arxiv.org/abs/2609.05335).
- **"Toward Scalable Automated Repository-Level Datasets" (Lbath, arXiv 2603.17974, Mar 2026)** — doctoral proposal to inject realistic vulns into real repos with PoV exploits; no data/results yet — [arXiv](https://arxiv.org/abs/2603.17974).
- **RepoAudit (ICML 2025)** — LLM agent auditing repos, with a validator for data-flow facts and path conditions; 40 true bugs in 15 real projects at 78.43% precision, 0.44 h and $2.54 per project; 185 new bugs (174 confirmed/fixed) in larger projects — [ICML poster](https://icml.cc/virtual/2025/poster/45170); [PMLR](https://proceedings.mlr.press/v267/guo25n.html). The talk summary says 38 true bugs with Claude 3.5 Sonnet (discrepancy) — [SlidesLive](https://slideslive.com/39041096). Code: github.com/PurCL/RepoAudit — [ICML poster](https://icml.cc/virtual/2025/poster/45170).
- **LLMxCPG (USENIX Security 2025)** — architecture closest to Orion: an LLM writes queries over a Joern-style code property graph to extract a slice, a second LLM classifies it; slices cut code 67.84-90.93%; 15-40% F1 gains over baselines on verified datasets; code at github.com/qcri/llmxcpg — [USENIX](https://www.usenix.org/conference/usenixsecurity25/presentation/lekssays); [Zenodo artifact](https://zenodo.org/records/15614095).
- **Exploit/PoC-centric (low fit for Orion, listed for completeness)** — CyberGym: 1,507 instances from 188 projects, agents get description + pre-patch codebase and must write a triggering PoC; best ~20% success; ICLR 2026 — [CyberGym](https://arxiv.org/html/2506.02548v2); [ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/c876a2935a90aff21874e14c07dc3e33-Abstract-Conference.html). SEC-bench and CVE-Bench are cited there as historical-vuln benchmarks with up to ~200 instances; SEC-bench's patch task lacks post-patch functionality tests — [CyberGym](https://arxiv.org/html/2506.02548v2); [CyberGym-E2E](https://arxiv.org/pdf/2606.04460). BountyBench is already adapted in Orion — [eval/bountybench.py](file:///C:/Users/h/Downloads/orion/eval/bountybench.py).

## Q2. Which benchmarks report false-positive rates on clean or patched code, and which provide patched twins so silence on fixed code can be measured?

### Takeaway
Patched-twin scoring is built into OpenSSF CVE Benchmark, Cisco's Vulnerability Localization Benchmark (Phase B TNR), DeepSource's OpenSSF-based benchmark (`fixed`/`unfixed`), and is derivable from CWE-Bench-Java (patches; QLCoder already scores "detect in vulnerable but not patched"), Vul4J/VJBench (human patch), JitVul (introducing/fixing pairs), ReposVul (pre/post patch) and Ghera (secure app). OWASP Benchmark and Juliet measure FPR on separately written safe cases, not patched twins. VulnGym and the Zhou et al. sets have no patched versions.

### Cited Findings
- OpenSSF CVE Benchmark scores a tool on both the vulnerable code (miss = FN) and the patched code (alert = FP) — [ossf-cve-benchmark](https://github.com/ossf-cve-benchmark/ossf-cve-benchmark).
- Cisco VLB Phase B: the agent must decide the recorded vuln is gone on the post-fix snapshot; TNR results: Semgrep 0.912, Semgrep-CWE 0.996, CodeQL 0.988, Horusec 0.980; GPT-5 Nano 0.868, GPT-5 0.743, GPT-5.5 (xhigh) 0.279, GPT-5.5 (default) 0.192; Granite-4.0-1B 1.000 (possibly refusing to engage); Antares 0.008-0.034 — [VLB HTML](https://arxiv.org/html/2609.15939). The authors note systems "still report unsupported locations on patched repositories" — [VLB abs](https://arxiv.org/abs/2609.15939).
- DeepSource's judged results carry `variant: fixed|unfixed` with TP/FP/TN/FN — [DeepSourceCorp/benchmarks](https://github.com/DeepSourceCorp/benchmarks).
- CWE-Bench-Java ships buggy commit + fix patches — [cwe-bench-java](https://github.com/iris-sast/cwe-bench-java); QLCoder counts a CVE solved only if its query detects it "in the vulnerable but not in the patched versions" (53.4% of 176 CVEs) — [QLCoder](https://arxiv.org/html/2511.08462v2).
- Vul4J entries include the human patch and PoV tests — [Vul4J](https://github.com/tuhh-softsec/vul4j); JitVul links each function to introducing and fixing commits — [JitVul](https://arxiv.org/abs/2503.03586); ReposVul is built from (untangled) patches — [ReposVul](https://arxiv.org/abs/2401.13169v2); Ghera's secure app is the patched variant — [Ghera](https://arxiv.org/pdf/1708.02380).
- OWASP Benchmark scoring is TPR - FPR over vulnerable and safe test cases — [OWASP wiki](https://wiki.owasp.org/index.php/Benchmark).
- SastBench's negatives are Semgrep findings on pre-fix code, labelled heuristically; some "negatives" may be real unreported bugs — [SastBench](https://arxiv.org/html/2601.02941v1).
- VulnGym does not use patched versions — [VulnGym HTML](https://arxiv.org/html/2608.02001). Zhou et al. treat all non-fix-touched functions as clean and use "marked function ratio" as an FP proxy — [Zhou et al.](https://arxiv.org/html/2407.16235v1).
- Sonar's internal ground truth explicitly lists expected-no-issue locations (true negatives) — [Sonar blog](https://www.sonarsource.com/blog/enhancing-sast-detection-leveraging-benchmarks-for-measuring-progress/).

### Inferences
- VLB's Phase B numbers show a strong recall/false-alarm trade-off for frontier LMs (GPT-5.5 xhigh: best File F1 but TNR 0.279) while SAST tools stay quiet on patched code (TNR >= 0.91) but localize poorly (File F1 <= 0.086). That is exactly the gap Orion's separate verifier is meant to close, so "Phase B TNR at a given Phase A F1" is a natural headline for model+Orion vs model alone.
- Orion's existing "patched_silence" gate (Gate 1) and vulnerable+patched manifest design align with OpenSSF / VLB / CWE-Bench-Java patched-twin scoring; those three can be scored with Orion's matcher without new labeling.

### Gaps
- Whether SecBench.js and CASTLE ship patched/safe twins was not verified.
- OpenSSF CVE Benchmark's exact per-CVE location format (file/line of the weakness) was not read.

## Q3. Which accept SARIF or have scorecard tooling that could score Orion's SARIF directly?

### Takeaway
Only OWASP Benchmark has mature, tool-agnostic-ish scorecard tooling (BenchmarkUtils), and it reads SARIF only through per-tool parsers (CodeQL, Semgrep, Snyk Code, Bandit, Contrast, Precaution, Semmle LGTM); no generic SARIF reader is documented. OpenSSF CVE Benchmark uses pluggable tool drivers; CWE-Bench-Java, VLB, VulnGym and SastBench use their own JSON/CSV formats. Orion would need a small adapter per benchmark (or to emit SARIF shaped like a supported tool).

### Cited Findings
- BenchmarkUtils compares each tool's results in `/results` with the suite's `expectedresults-##.csv` and writes scorecards to `/scorecard`; GPL-3.0 — [BenchmarkUtils](https://github.com/OWASP-Benchmark/BenchmarkUtils).
- SARIF inputs listed: Bandit (.sarif), CodeQL (.sarif), Contrast CodeSec/Scan (.json SARIF), Precaution (.sarif), Semgrep Code (.sarif or .json), Snyk Code (.sarif), Semmle LGTM (.sarif); other tools via XML/JSON (SonarQube .xml, SpotBugs .xml, Horusec .json, Fortify .fpr, Checkmarx .xml, Coverity .json, Veracode .xml, etc.); generic SARIF support not stated — [OWASP tool-support tab](https://raw.githubusercontent.com/OWASP/www-project-benchmark/master/tab_tool_support.md).
- The BenchmarkUtils README does not document how to add a new tool parser — [BenchmarkUtils](https://github.com/OWASP-Benchmark/BenchmarkUtils).
- OpenSSF CVE Benchmark ships drivers for ESLint, NodeJSScan and CodeQL and invites new drivers — [ossf-cve-benchmark](https://github.com/ossf-cve-benchmark/ossf-cve-benchmark).
- VLB's agents submit through `submit_vulnerable_files` / `submit_no_vulnerability_found` tools — [VLB HTML](https://arxiv.org/html/2609.15939).
- CWE-Bench-Java ground truth is CSV (`fix_info.csv`, `project_info.csv`) — [cwe-bench-java](https://github.com/iris-sast/cwe-bench-java).
- Orion already writes `<run_dir>/results.sarif` (CONFIRM = error, INCONCLUSIVE = warning) and has a normalizer/matcher that reads Orion verdicts and plain-agent `findings.json` — [Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md).

### Inferences
- Cheapest path to an OWASP scorecard: emit Orion SARIF using the same result/rule/CWE tagging as Semgrep or CodeQL SARIF so an existing BenchmarkUtils SARIF parser accepts it, or add an "Orion" parser class; the scorecard then gives Youden / TPR / FPR directly comparable with the tools above.
- For everything else, Orion's own `eval/normalize` + `eval/match` path (file + function or line +/-10, CWE family) is a stricter and more uniform scorer than each benchmark's native script; VLB's File F1 and VulnGym's k=5-line recall can be recomputed from Orion SARIF.

### Gaps
- Whether BenchmarkUtils has an undocumented generic SARIF reader (source under `library/.../parsers` returned 404 at the guessed path) — check the source tree.
- How BenchmarkUtils maps a finding to a test case (file-name + CWE is the usual practice, but not verified here).
