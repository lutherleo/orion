# Fresh CVEs and patched twins test Orion

The best benchmarks for showing whether Orion makes a model better than the same model alone are whole-repository security sets that pair each vulnerable snapshot with its patched twin, in Orion's languages. Five of them fit: Cisco's **Vulnerability Localization Benchmark (VLB: 500 GitHub advisories in 290 repos, file-level ground truth plus a test of silence on the patched snapshot, with 27 language models and 4 SAST tools already scored)**, **CWE-Bench-Java** (120 Java CVEs with method and line fix ranges; CodeQL finds 27), the **OpenSSF CVE Benchmark** (218 JS/TS CVEs, before and after the patch), **PyVul** for Python, and **OWASP Benchmark Java/Python** as the false-alarm set; a sixth, **VulnGym**, has the closest design (line-level entry-to-sink traces) but no released data yet. All of them predate the May 2026 frontier training cutoff, so they work only as development and control sets; the one contamination-clean test is still Orion's own post-2026-05-31 manifest, or a fresh mine that reuses VLB's open advisory pipeline. VLB's published numbers expose exactly the gap Orion is built to close: the best frontier model localizes best (File F1 0.229) but stays silent on only 28% of patched repos, while SAST tools stay silent on 91–99% of them but localize poorly (File F1 at most 0.086), so Orion's headline should be "silent on patched code at matched recall," not recall alone. Memory, long-context, RAG and GraphRAG benchmarks cannot test Orion directly, because they run on prose or chat logs and every GraphRAG benchmark builds its graph from text with an LLM rather than by program analysis; what they offer are the experiment designs that make a claim credible (repo-size sweeps, clues that share no words with the question, ablations of each path to the code, a strong grep-agent baseline and oracle-evidence splits), plus direct component tests for two of Orion's layers: CoIR and RepoQA for `semantic_search`, and CypherBench, Mind the Query and Neo4j Text2Cypher for Cypher writing. Published code-graph studies warn that gains are real but shrink as models grow (+17–21 points over grep at 1.7–4B parameters, +4–5 at 32B), so any Orion study needs grep-only and embedding-only arms. UK AISI's Inspect (`inspect_swe.claude_code()`) or Harbor can run the arms, but scoring should stay in Orion's `eval/`, with paired, repo-clustered, exact statistics, because tens of vulnerabilities can reveal only large effects. One family is under-covered: the dedicated notes on agentic and offensive benchmarks (BountyBench, CyberGym, CVE-Bench, Cybench, CTF suites) were never written, so this report treats them only from fragments in the other notes, and that is a gap.

## Six of about 45 vulnerability sets fit Orion's whole-repo task

A benchmark can answer "does Orion make model X better than X alone" only if it has four things at once. It needs **whole repositories**, because Orion's value is the cross-file code graph and a lone function has no graph worth building. It needs **Orion's languages**: marker detection covers JS/TS, Python, Java and Go, and the pre-registered study admits only JS/TS, Python and Java ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). It needs **fix-site ground truth** at file, function or line, so Orion's file/line/function/CWE findings can be matched. And it needs **safe or patched code**, so false alarms are scored rather than ignored. The research notes checked about 45 vulnerability datasets and benchmarks, and six pass all four tests or come close.

The six do different jobs. VLB, CWE-Bench-Java, OpenSSF and PyVul test recall and silence on real CVEs. OWASP is a false-alarm and regression set whose seeded cases are written to be actually exploitable ([OWASP Benchmark project](https://owasp.org/www-project-benchmark/)), and its Python suite lists counts per CWE, from 16 SQL-injection cases to 326 weak-randomness cases ([OWASP Python tab](https://raw.githubusercontent.com/OWASP/www-project-benchmark/master/tab_python_test_cases.md)). VulnGym has the best design for Orion but is the least usable today, because the paper gives no dataset link and names no languages ([VulnGym](https://arxiv.org/html/2608.02001)).

VLB needs two adjustments for Orion's study. Its **244 Maven, npm and pip tasks** fit the study's language rule, the 215 Go tasks fit Orion's golang frontend but not the study, and the 40 Rust tasks are out ([VLB](https://arxiv.org/html/2609.15939v1)). Its file-level ground truth also under-credits Orion, which reports functions and lines. Because VLB's code and fix diffs are public, Orion can derive function and hunk ranges from the same diffs and report both granularities, which also makes the results comparable with VulnGym's 5-line rule and Orion's own ±10-line matcher. CWE-Bench-Java has practical costs of its own: it needs Linux and three manually downloaded Oracle JDKs ([cwe-bench-java](https://github.com/iris-sast/cwe-bench-java)), and its CVEs are old enough to be memorized. When citing IRIS, use the ICLR camera-ready figure of 55 of 120, not the preprint's 69 ([ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/582d4e27fa24168f3af1f4582655034b-Abstract-Conference.html)). Data licenses were confirmed for only a few sets (CWE-Bench-Java and OpenSSF are MIT, OWASP Java is GPL-2.0 and OWASP Python is GPL-3.0 ([BenchmarkPython](https://github.com/OWASP-Benchmark/BenchmarkPython))); the rest are unchecked.

### VLB shows frontier models trade silence for recall

VLB is the closest public mirror of Orion's own eval design. Each task pairs the commit just before the fix with the fix commit: Phase A scores File F1 on the vulnerable snapshot, and Phase B asks the agent to judge that the vulnerability is gone from the patched one ([VLB](https://arxiv.org/html/2609.15939)). The results split cleanly. **GPT-5.5 at its highest ("xhigh") reasoning-effort setting localizes best (File F1 0.229, precision 0.310, recall 0.221) but stays silent on only 27.9% of patched repos**, while GPT-5 reaches 0.743 TNR and GPT-5 Nano 0.868. **SAST tools are the mirror image: Semgrep, CodeQL and Horusec stay silent on 91–99% of patched snapshots but reach File F1 of only 0.020–0.086** ([VLB](https://arxiv.org/html/2609.15939)). Cisco's small specialized localizer, Antares-3B, nearly matches GPT-5.5 on File F1 (0.223) at under $0.002 per task, yet its silence on patched code is 0.008–0.034, which means it almost never says "fixed" ([VLB](https://arxiv.org/html/2609.15939); [Antares](https://arxiv.org/abs/2608.02407)). **No model localized 38.4% of tasks** ([VLB abstract](https://arxiv.org/abs/2609.15939)). That trade-off is exactly the gap Orion's separate verifier is meant to close, so the natural Orion headline on VLB is patched-snapshot TNR at a matched File F1, not F1 alone.

VLB gave its agents only a read-only terminal (ls, find, grep, sed, cat; 15 commands, 20 turns, no network) and no graph or retrieval tool ([VLB](https://arxiv.org/html/2609.15939v1)). An arm that swaps that terminal for Orion's read-only graph tools, with the same model and the same budget, is therefore a clean A/B test that nobody has run. Costs are already published: the GPT-5.5 (xhigh) sweep cost about $141 and 5 hours, and GLM-5.2 about $12.50 and 50 minutes ([VLB](https://arxiv.org/html/2609.15939)).

A vendor study gives a "model alone" reference outside VLB, with caveats. On 11 large Python web apps, Claude Code (Sonnet 4) reported 46 real vulnerabilities at a 14% true-positive rate, and repeated runs on one app gave 3, 6 and 11 findings ([Semgrep](https://semgrep.dev/blog/2025/finding-vulnerabilities-in-modern-web-apps-using-claude-code-and-openai-codex)). It is a single-run study by a vendor that sells deterministic analysis, so it frames the noise problem rather than setting a baseline. Orion's own NodeGoat result (14 of 15 found, zero true false positives) is likewise a dev number on a well-known, memorizable app ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)).

Feeding Semgrep or CodeQL output to Orion's verifier alone would separate the verifier's contribution from discovery's.

### Function-level, synthetic and exploit-scored sets fit poorly

The classic machine-learning vulnerability datasets (Devign, BigVul, Draper VDISC, ReVeal, VulDeePecker/SySeVR, D2A, DiverseVul, PrimeVul, MegaVul, CleanVul and VulnPatchPairs) and most LLM vulnerability evals (SecVulEval, VulDetectBench, SecLLMHolmes, VulnLLMEval, LLM4Vuln and VulBench) are isolated functions or snippets, mostly in C/C++ ([PrimeVul](https://arxiv.org/html/2403.18624v2); [SecVulEval](https://arxiv.org/html/2505.19828v1)). None of them can show a graph's benefit. Many keep project and commit IDs, so whole-repo tasks could be rebuilt from them, but that fixes the missing context, not the label noise or the language mismatch. Their lasting value is in method. PrimeVul's pair-correct metric counts a hit only if the vulnerable function is flagged and its patched twin is not, and on it GPT-4 with chain of thought scored 12.94%, below the 22.70% random baseline ([PrimeVul](https://arxiv.org/html/2403.18624v2)). SecLLMHolmes found that simple renames flipped GPT-4's answer 17% of the time ([SecLLMHolmes](https://arxiv.org/pdf/2312.12575)). LLM4Vuln explicitly separates a model's vulnerability reasoning from knowledge retrieval and tool use, which is the "with Orion vs without" question in miniature ([LLM4Vuln](https://arxiv.org/pdf/2401.16185)).

Synthetic suites work only as false-alarm checks. NIST Juliet 1.3 has 64,099 C/C++ and about 28,900 Java cases ([Juliet 1.3](https://samate.nist.gov/SARD/downloads/documents/releaseJuliet1.3Doc.txt)), and CASTLE has 250 C micro-programs over 25 CWEs ([CASTLE](https://arxiv.org/abs/2503.09433v2)). Even Juliet's answer list is unreliable: NIST's own SATE VI analysis found "thousands of errors" in the manifest of known bugs for Juliet 1.3 C ([NIST SATE VI](https://www.nist.gov/document/sate-vi-presentation-08ockham)).

**Agentic and offensive benchmarks are a known gap in this report.** The researcher assigned to them never wrote their notes, so what follows comes only from fragments in the other notes. CyberGym gives an agent a vulnerability description and a pre-patch codebase and asks for a crashing proof-of-concept (PoC); it has 1,507 instances from 188 projects, and the best systems succeed about 20% of the time ([CyberGym](https://arxiv.org/html/2506.02548v2)). SEC-bench scores PoC generation (best 18.0%) and patching (best 34.0%), with no localization task ([SEC-bench](https://arxiv.org/pdf/2506.11791v2)). T2L-ARVO shows that this C/C++ fuzzing family can be re-scored for localization, reaching 54.8% line-level localization on 50 expert-verified cases ([T2L-ARVO](https://arxiv.org/html/2510.02389v3)). CVE-Bench, ExploitBench, Cybench, the Google DeepMind (GDM) in-house CTF, InterCode CTF and 3CB ship as ready tasks in inspect_evals ([inspect_evals catalog](https://ukgovernmentbeis.github.io/inspect_evals/)), and an audit of CVE-Bench with the Agentic Benchmark Checklist cut its performance overestimation by 33% ([Zhu et al.](https://arxiv.org/abs/2507.02825)). DARPA's AIxCC final used 63 synthetic vulnerabilities, of which teams found 54, but release of its data was promised and is unconfirmed ([DARPA](https://www.darpa.mil/news/2025/aixcc-results)). BountyBench is already adapted inside Orion as a localization dev benchmark, with answer keys built and nothing run ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). Most of this family is C/C++ and scored by exploit success, and Orion writes no exploits by design, so its likely role is localization re-scoring rather than head-to-head use. Their current leaderboards, cost conventions, task formats, licenses and dates against the cutoff were not researched.

## No public benchmark postdates the May 2026 cutoff

Orion's dataset rule treats anything public before 2026-05-31 as possibly memorized by Opus 5-class models ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). By that rule every catalogued benchmark is a development or control set. The freshest are VulnGym, whose advisories run from November 2025 to April 2026 and are "post-cutoff" only for the models its authors tested ([VulnGym](https://arxiv.org/html/2608.02001)); VLB, which spans 2016–2026 with 21 tasks from 2026 in months that were not read ([VLB](https://arxiv.org/html/2609.15939v1)); SastBench, with CVEs after February 2025 ([SastBench](https://arxiv.org/html/2601.02941v1)); and the 2022–2026 CVE set behind "The History Is the Detector" ([arXiv 2609.05335](https://arxiv.org/abs/2609.05335)). OpenSSF's per-CVE repos date from December 2020 ([ossf-cve-benchmark org](https://github.com/ossf-cve-benchmark)), and the OWASP answer files sit in public repos. Older time-split designs such as PrimeVul and VulEval no longer protect anything, because their test windows predate today's cutoffs.

Contamination does not hit both arms equally. On SWE-bench Verified, models name the buggy file from the issue text alone up to 76% of the time, against at most 53% on repos outside the benchmark ([arXiv 2506.12286](https://arxiv.org/abs/2506.12286)); OpenAI stopped reporting Verified in February 2026 ([OpenAI](https://openai.com/en/index/why-we-no-longer-evaluate-swe-bench-verified)), and Epoch rates it "Flawed" ([Epoch](https://epoch.ai/benchmarks/swe-bench-verified/review)). Recall from memory substitutes for retrieval, so it inflates the no-tool arm and shrinks the measured value of any retrieval tool. A graph gain on a public set is therefore a conservative estimate, and a null result there is not conclusive. The counterpoint deserves weight: a matched-control re-analysis found that one reported +10-point localization gap on Verified had a 95% interval that included zero ([arXiv 2610.05830](https://arxiv.org/abs/2610.05830)), so contamination claims need evidence of where the data came from, not just a score gap.

Agents also take shortcuts when they can. "Shortcutting the Fix" found shortcut attempts (fetching upstream fixes, mining local Git history, recalling memorized code) in 60.7–90.1% of trajectories on SWE-bench Multilingual, and up to 72.1% of tasks were resolved with a shortcut's help. Turning off the network did not stop the attempts, while telling agents to work independently cut them to 9.4–14.2% ([arXiv 2609.06780](https://arxiv.org/abs/2609.06780)). Orion's own audit found the same leak, with fix commits visible through `.git` in checkouts ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). Any adopted benchmark therefore needs `.git` stripped, web access denied and file reads confined, whatever its native harness does. The Agentic Benchmark Checklist shows the stakes: task-setup and reward flaws mis-estimate agent performance by up to 100% in relative terms ([Zhu et al.](https://arxiv.org/abs/2507.02825)).

Label quality is the other trap. Marking every function a fix commit touched as vulnerable yields 40–75% noise ([CleanVul](https://arxiv.org/html/2411.17274v3)). Manual checks found correct labels on only 25% of BigVul samples, 24% of CodeXGLUE/Devign, 47.8% of CrossVul, 51.7% of CVEfixes and 60% of DiverseVul, against 86–92% for PrimeVul's cleaned labels, and CVEfixes' test set carried 18.9% exact duplicates ([PrimeVul](https://arxiv.org/html/2403.18624v2)). The consequence is dramatic: StarCoder2 scored 68.26% F1 on BigVul and 3.09% on PrimeVul ([PrimeVul](https://arxiv.org/html/2403.18624v2)). Diff-derived truth such as VLB's inherits tangled patches, where files changed only for refactoring count as "vulnerable," so Orion's fix-site convention should be applied before line-level scoring. A correct label is also not a correct finding: in DREA's repo pairs, 26–55% of true positives came with flawed reasoning ([arXiv 2607.13439](https://arxiv.org/abs/2607.13439)), which argues for matching on location and CWE rather than yes/no labels.

Orion-LM adds its own leak. C1 was trained on pairs derived from MoreFixes and OSV ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)), and VLB, VulnGym, eyeballvul, PyVul, ReposVul and CWE-Bench-Java are all built from the same kinds of advisory and fix-commit sources ([MoreFixes](https://zenodo.org/records/13983082)), so every item must be checked against Orion's leak set (canonical repo plus fix commit) before an `orion-lm` arm is scored. The clean options are few. The first is Orion's own manifest of 208 dataflow and 50 access-control rows with advisory and fix after 2026-05-31 ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). The second is a re-run of VLB's published GHSA-plus-fix-commit pipeline on post-cutoff advisories. The third is a date-pinned eyeballvul slice, if its weekly refresh continues ([eyeballvul](https://pypi.org/project/eyeballvul)). For generic localization, SWE-bench-Live's monthly additions of 50 verified issues ([SWE-bench-Live](https://arxiv.org/abs/2505.23419)) and SWE-rebench's continuously refreshed leaderboard ([SWE-rebench](https://arxiv.org/abs/2505.20411)) supply fresh tasks. Renamed variants in the style of VJBench-trans ([VJBench](https://arxiv.org/html/2305.18607v2)), a canary string embedded in manifests and answer keys ([BIG-bench](https://github.com/google/BIG-bench)), and a probe that asks the plain model to name the CVE without seeing the code add cheap secondary checks.

| [MemDev-Bench](https://arxiv.org/abs/2610.27524) (Oct 2026) | 555 base + 4,869 executable historical tasks for code-agent memory | Memory mainly improves fine-grained localization and editing | Medium: the one memory benchmark built on code |

Other code families fit less well. Repo-level completion benchmarks (CrossCodeEval, RepoBench, RepoEval, CoderEval, EvoCodeBench, DevEval, REPOCOD) would need a completion harness Orion lacks, and the target file would have to be removed before the build so the graph does not contain the answer. Function-corpus retrieval sets (CodeSearchNet, CoSQA, CLARC, CoREB) test the embedder, not the graph. BigCodeBench, ClassEval and LiveCodeBench make useful negative controls, because without a repo the graph should add nothing ([BigCodeBench](https://arxiv.org/abs/2406.15877); [LiveCodeBench](https://arxiv.org/abs/2403.07974)).

The published evidence for code graphs is consistent but modest. CodexGraph, the public system most like Orion (a Neo4j graph the LLM queries with Cypher), lifted GPT-4o's CrossCodeEval exact match from 10.80 with no retrieval, and 21.20 with BM25 keyword search, to **27.90**. The same system made Qwen2-72B worse than no retrieval at all (5.00 vs 8.20), and its authors list the failure modes: unbounded query output, loops that never produce a runnable query, weak models writing bad queries, and indexing that ran out of memory on some samples ([CodexGraph](https://arxiv.org/html/2408.03910v3)). Orion's bounded `run_cypher` (row caps, streaming) already addresses the first of these. RepoGraph added only **2.0–2.7 points** of resolve rate on SWE-bench Lite across four agent systems, at slightly higher cost ([RepoGraph](https://arxiv.org/html/2410.14684v2)). LocAgent's graph raised function-level Acc@10 on Lite to 77.37 against OpenHands' 70.07, but SweRank, a plain retrieve-and-rerank model with no graph, reached **88.69** ([LocAgent](https://arxiv.org/html/2503.09089v2); [SweRank](https://arxiv.org/html/2505.07849v2)). And a study of six localization methods over 16,248 repair trajectories found that better localization does not reliably improve repair, while current localization methods often spend more tokens than they save ([arXiv 2610.25826](https://arxiv.org/abs/2610.25826)).

The most useful single study for Orion, from October 2026, held a small localization agent fixed and varied only its tools across 79,000 episodes on SWE-bench Verified: grep and file reads only (G), G plus semantic search (E), G plus graph lookup and 1–2-hop neighbours (T), or everything (ET) ([arXiv 2610.33958](https://arxiv.org/abs/2610.33958)).

| Model | G (grep) | E (+ embeddings) | T (+ graph) | ET (all) |
|---|---|---|---|---|
| Qwen3-4B | 26.8 | 29.1 | 37.1 | 36.5 |
| Qwen3-32B | 32.0 | 35.7 | 34.0 | 35.9 |

Across the models tested, **structured tools beat grep by 17–21 points at 1.7–4B parameters but by only 4–5 points at 32B**. The gains came mostly from looking names up directly (zero hops) or expanding one hop. Each extra hop between the code the issue mentions and the function that changed cut the odds of success by a third to a half under every tool set, and agents chained graph expansions in only 12–14% of episodes ([arXiv 2610.33958 HTML](https://arxiv.org/html/2610.33958v1)).

Three implications follow for Orion. First, the study needs grep-only and embedding-only arms, or a graph win cannot be credited to the graph; Orion's plain arms and `--semantic-mode` already make both possible ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). Second, Orion-LM is testable from both sides: built on a 4B Qwen base, it sits in the size band where graph tools helped most in that study, and also where CodexGraph shows weak models write the worst queries. Third, Orion's distinctive feature is still untested, because none of the localization graphs above carries data flow; LocAgent's schema is contain/import/invoke/inherit, and CodexGraph's has no call edges ([LocAgent](https://arxiv.org/html/2503.09089v2); [CodexGraph](https://arxiv.org/html/2408.03910v3)). Orion's FLOWS_TO taint paths are what set it apart, and the depth study suggests generic issue localization rarely needs them, so Orion's advantage should show on source-to-sink tasks (VLB, VulnGym, SWE-Flux's dataflow questions), with results stratified by flow depth.

The security-specific evidence points the same way. LLMxCPG, which lets an LLM query a Joern-style code property graph for code slices, reports 15–40% F1 gains over baselines with slices 67.84–90.93% smaller than the full code ([USENIX Security 2025](https://www.usenix.org/conference/usenixsecurity25/presentation/lekssays)). "Graph Is the Verifier" reports that 71.7% of vulnerable functions need evidence from outside the function itself ([arXiv 2607.26656](https://arxiv.org/abs/2607.26656)), and JitVul found that ReAct agents with interprocedural context beat plain LLMs ([JitVul](https://arxiv.org/abs/2503.03586)). No paper found evaluates a Joern CPG as agent memory on any localization benchmark, so that slot is open.

## Memory and long-context benchmarks lend designs, not data

The memory and long-context literature cannot test Orion directly, because none of it contains code that would justify a program-analysis graph. Its shared headline still motivates Orion's design: models use far less context than they claim to handle. LongBench Pro found effective context length below the claimed length across 46 models ([LongBench Pro](https://arxiv.org/abs/2601.02872)). NoLiMa made the hidden fact share no words with the question, and at 32K tokens 11 of 13 models that claim 128K-token windows fell below half their short-context score, with GPT-4o dropping from 99.3% to 69.7% ([NoLiMa](https://arxiv.org/abs/2502.05167)). On code, LongCodeBench saw Claude 3.5 Sonnet fall from 29% to 3% as context grew toward 1M tokens ([LongCodeBench](https://arxiv.org/abs/2505.07897)), and LongCodeU found performance "drops dramatically" beyond 32K tokens ([LongCodeU](https://arxiv.org/abs/2503.04359)).

### Two Orion layers have direct component tests

The retrieval layer and the Cypher-writing layer can each be tested on their own. CoIR (10 datasets, 8 retrieval tasks, MTEB-compatible) can score Orion's chunk embedder and its vector, keyword and hybrid modes in isolation from the scanner ([CoIR](https://arxiv.org/abs/2407.02883)), and RepoQA tests `semantic_search` against a 16K-token in-context baseline. CypherBench and Mind the Query score Cypher writing by executing the queries against real graphs. Neo4j's Text2Cypher is a quick regression check, but it has been public since December 2024 and is probably in training data, and its train and test sets share one distribution ([Text2Cypher](https://arxiv.org/abs/2412.10064)). None of these uses a code property graph, and all of them assume one graph per database, while Orion's guard refuses any query not anchored to a `scan_id` ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). Running them through Orion's real tool path therefore needs either a loader that stamps a `scan_id` or scoring outside the guard, which then no longer tests the guard. The more valuable move is to generate a question set from Orion's own NodeGoat and PyGoat graphs: PIPE-Cypher turns a live property graph into a text-to-Cypher benchmark ([listing](https://papers.cool/arxiv/2606.08481); its arXiv ID is unconfirmed), and Mind the Query releases its synthesis pipeline. A set built this way is post-cutoff by construction and tests exactly the Cypher that Orion-LM, a 4B model, has to write.

### Eight borrowed designs become extra arms, not new benchmarks

Each design below slots into Orion's existing `eval/` as an extra arm or stratum.

Two cautions from the memory literature shape these designs. The first is that the baseline that matters is a capable agent, not a naive one. Letta reported that a plain agent with files and grep scored 74.0% on LoCoMo with GPT-4o mini, against 68.5% reported for Mem0's graph-memory variant ([secondary summary](https://www.agenticwire.news/article/mem0-zep-letta-agent-memory)), and one of the GraphRAG-Bench papers was motivated by GraphRAG "frequently underperform[ing] vanilla RAG on many real-world tasks" ([Xiang et al.](https://arxiv.org/abs/2506.05690)). The second is that cost belongs next to accuracy. Mem0 reports more than 90% token savings and 91% lower p95 latency than a full-context baseline ([Mem0](https://arxiv.org/abs/2504.19413)), LongMemEval measured a 30% accuracy drop over sustained interactions for commercial assistants ([LongMemEval](https://arxiv.org/abs/2410.10813)), and Microsoft built LazyGraphRAG specifically to avoid "prohibitive up-front indexing costs" ([BenchmarkQED](https://www.microsoft.com/en-us/research/?p=1140429)). Orion's equivalent of indexing cost is Joern build time, which belongs in the per-scan cost rather than being hidden.

For the plain arms, Inspect with `inspect_swe.claude_code()` is the closest off-the-shelf match to "the same model without Orion." It gives one container per repo and accounts for tokens through its proxy, which would replace Orion's `claude` usage shim, and its default withholding of provider-side web tools helps with the known problem of frontier agents having web access. Two traps need attention: the bridge silently drops sampling settings unless `forward_generation_config=True` is set, which would quietly break a pre-registered frozen-sampling rule, and Claude Code's own client-side web tools still need container network rules. The Orion arm is heavier, because Neo4j, Joern and a model cannot run together on the 16 GB M4, so phased runs against an external Neo4j are more realistic than full isolation per task ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). Orion-LM's in-process MLX model cannot use the bridge at all, since the bridge speaks only the OpenAI, Anthropic and Google APIs ([Inspect](https://inspect.aisi.org.uk/agent-bridge.html)), so `eval/arms/lm.py` should stay in-process. Scoring stays home: no harness ships a scorer that compares SAST findings with an answer key. For the OWASP scorecard, the cheapest path is to emit SARIF shaped like Semgrep's or CodeQL's so an existing BenchmarkUtils parser accepts it, or to add an Orion parser class; everything else goes through `eval/normalize` and `eval/match`, consistent with decision D5.

### Tens of vulnerabilities detect only large effects

Small benchmarks need paired, clustered and exact statistics. Miller recommends comparing arms on question-level paired differences with standard errors clustered by group; in his examples clustering changed the standard error by factors of 3.05, 1.88 and 1.10. His power analysis is sobering: detecting a 3-point gap at 80% power needs about 969 independent questions, and with 198 items, resampling each one 10 times instead of once shrinks the minimum detectable effect from 13.2 to 7.5 points ([Miller](https://arxiv.org/html/2411.00640v1)). VLB's 244 in-scope tasks, or Orion's 258-row manifest, can therefore detect only large effects unless each arm runs several times, which Orion's three-runs-per-arm protocol already does. Below a few hundred datapoints, normal-approximation (CLT) intervals "dramatically underestimate" uncertainty, so exact or Bayesian intervals are the safer choice ([Bowyer et al.](https://arxiv.org/abs/2503.01747)). The recommended tests are an exact McNemar test on the vulnerabilities where the arms disagree ([Dietterich](https://doi.org/10.1162/089976698300017197)), pass@1 averaged over runs alongside pass^3 ("caught in all three runs") as a reliability measure ([τ-bench](https://arxiv.org/abs/2406.12045)), and a Holm correction across ablations. Orion already has a paired cluster bootstrap that resamples repos (B = 10,000) ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)), though its coverage with fewer than about ten repos has not been validated anywhere the researchers found.

### Report dollars on a Pareto frontier, not proxies

Cost reporting should follow Kapoor et al. and HAL: dollars rather than proxies, plotted on a cost-accuracy Pareto frontier ([Kapoor et al.](https://arxiv.org/html/2407.01502v1); [HAL](https://hal.cs.princeton.edu/)). Orion's own repricing shows why exact pricing matters: `claude -p` writes its one-hour cache at 2x, so the NodeGoat and PyGoat Opus runs cost $0.73 and $1.01, not $0.61 and $0.84 ([Orion CLAUDE.md](file:///C:/Users/h/Downloads/orion/CLAUDE.md)). A credible results table follows IRIS's layout but closes its gaps ([IRIS](https://arxiv.org/abs/2405.17238)). Its rows are the plain model, full Orion, one-off ablations (graph off, semantic search off, verifier off, shortlists, runtime) and Semgrep and CodeQL as non-LLM anchors. Its columns are location-only and right-CWE catches, pair-correct, false alarms on patched twins and OWASP, tokens, dollars and vulnerabilities per million tokens, dollars per confirmed true finding, and wall time. The researchers found no 2024–2026 security paper that combines a same-model tool-on/tool-off comparison with clustered intervals and McNemar; that absence comes from a limited search, but it suggests the design itself is a contribution.

## Conclusion

The literature changes what Orion should claim. "Orion finds more bugs" is the wrong winning claim, because graph tools add little recall for large models and frontier models already localize well. The claim the evidence supports is about calibration. VLB shows frontier models giving up silence on patched code to gain recall, and SAST tools giving up recall to stay silent, and nobody has yet put a graph-grounded discovery stage and a separate verifier between those two extremes and measured where it lands. The pre-registered headline should therefore be silence on patched code at matched recall, scored as pair-correct, with VLB's 244 in-language tasks as the public yardstick and the post-cutoff manifest as the test that counts.

Two asymmetries tell Orion how to read its future results. Contamination favours the plain arm, so a gain on any public benchmark understates Orion's value: a null result there is weak evidence, while a null on the post-cutoff manifest would be strong. Graph benefit concentrates in small models and short hops, so the open-weight claim (Orion-LM plus the graph versus frontier models alone) has more room to win than the Opus-plus-Orion comparison, and is also more exposed to the bad-query failure CodexGraph documented. The unclaimed ground is a Joern CPG with real data flow, used as agent memory and tested on source-to-sink localization against grep and embedding baselines. Every piece that experiment needs already exists in Orion except the arms themselves and the agentic-benchmark research this report could not cover.
